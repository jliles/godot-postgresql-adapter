# PostgreSQL GDExtension for Godot

This extension lets a Godot 4 game talk to a PostgreSQL database. It's written in C++ on top
of libpqxx and gives you parameterized queries, a connection pool, transactions, and queries
that run in the background without freezing your game. When something goes wrong, you get an
error message instead of a crash.

## Requirements

- Godot 4.7 or newer. The extension is compiled against the exact engine you run, and assumes
  a double-precision engine build by default. If you use a standard engine build, pass
  `precision=single` to `scons`.
- A C++20 compiler and SCons.
- Linux. The extension runs on the game server only; game clients shouldn't talk to the
  database directly, so export them without this addon.
- curl, git, make and the OpenSSL development headers (`libssl-dev` on Debian and Ubuntu,
  `openssl-devel` on Fedora, `openssl` on Arch). They're used to build the PostgreSQL client
  libraries.

## Building from source

```bash
# Fetch godot-cpp
git submodule update --init --recursive

# Describe your engine's API to the build. Run this again whenever you update Godot.
godot --headless --dump-extension-api

# Builds the client libraries the first time, then the extension itself
./build_scripts/build_linux.sh
```

If you'd rather run the steps yourself, run `build_scripts/build_third_party.sh` once, then
`scons platform=linux target=template_debug` and `scons platform=linux target=template_release`.
Run `scons` from the top of the repository, not from inside `godot-cpp/`; the top-level build
compiles godot-cpp for you, against your engine's API. The finished libraries end up in `addons/godot-postgresql/bin/`.

`third_party/` and `extension_api.json` are generated by these steps, so they aren't checked
into git.

To use the extension in a game, copy the `addons/godot-postgresql/` folder, including the
built `bin/` folder, into your project.

You don't need PostgreSQL installed on the server. The client libraries are built into the
extension itself. The only thing it needs from the system, apart from the standard C library,
is OpenSSL 3, which nearly every Linux system already has (see [Dependencies](#dependencies)).

## Usage

`PostgresqlAdapter` is a node. You can add it to a scene, or create one in code with
`PostgresqlAdapter.new()`; if you do, remember to free it when you're done.

```gdscript
var db := PostgresqlAdapter.new()

func _ready():
    db.connection_string = "postgresql://username:password@localhost:5432/database"
    db.pool_size = 4
    if not db.connect_to_db():
        push_error("Database unreachable: " + db.get_last_error())
        return
    var rows: Array = db.execute_query("SELECT name FROM users WHERE active = $1", [true])
    if db.get_last_error() != "":
        push_error(db.get_last_error())
    for row in rows:
        print("User: ", row["name"])
```

If you place the adapter in a scene with its connection string already filled in, it connects
on its own when it enters the scene tree.

### Handling errors

SQL errors, dropped connections and timeouts never crash the game. Instead, a failed query
returns an empty array, and a failed non-query (such as an `INSERT` or `UPDATE`) returns `-1`.
Call `get_last_error()` to find out what happened. Every call clears the previous error, so
after a successful call it's empty.

Some failures are also reported through signals. Queries inside a transaction emit
`query_failed` or `non_query_failed`, problems starting or ending a transaction emit
`transaction_failed`, and failing to get a database connection emits `connection_error`.

### The connection pool

The adapter keeps a pool of database connections and opens them only as they're needed, up
to `pool_size`. `connect_to_db()` returns `true` only if it really could open a connection.

When every connection is busy, a call waits for one to free up. It waits for up to
`acquire_timeout_ms` (5 seconds by default), and then gives up with a timeout error rather
than hanging. If a connection has broken, for example because the database server restarted,
it's thrown away and replaced, and the query is automatically tried once more on a fresh
connection.

Changing `connection_string` or `pool_size`, or calling `disconnect_from_db()`, closes the
whole pool. If a transaction is open at that moment, it's rolled back and a warning is
printed. Background queries that are already running are allowed to finish, and ones still
waiting to start are cancelled. The next call opens a new pool.

### Transactions

Normally, each call to `execute_query` or `execute_non_query` is saved to the database as
soon as it finishes. To group several statements so that they all succeed or all fail
together, use a transaction:

```gdscript
if db.begin_transaction():
    db.execute_non_query_in_transaction(
        "INSERT INTO users (name, email) VALUES ($1, $2)", ["John Doe", "john@example.com"])
    db.execute_non_query_in_transaction(
        "UPDATE user_stats SET login_count = login_count + 1 WHERE user_id = $1", [user_id])
    db.commit_transaction()   # or db.rollback_transaction() to undo everything
```

A transaction keeps one connection from the pool to itself until you commit or roll it back.
Each adapter can only have one transaction open at a time; `is_in_transaction()` tells you
whether one is open.

Use each adapter from a single thread. If you want work to happen in parallel, use the
background queries described below, or give each of your threads its own adapter.

### Background (async) queries

`execute_query_async` and `execute_non_query_async` return straight away, so your game keeps
running while the database does the work. Each call gives you back a request ID. When the
query finishes, the adapter emits a signal on the main thread with that ID, so you can tell
which result belongs to which request:

```gdscript
db.query_completed.connect(func(id: int, rows: Array): print(id, ": ", rows.size(), " rows"))
db.non_query_completed.connect(func(id: int, count: int): print(id, ": ", count, " rows changed"))
db.async_query_failed.connect(func(id: int, query: String, error: String): push_error(error))

var id := db.execute_query_async("SELECT * FROM large_table WHERE zone = $1", [zone])
```

A few things to know:

- Up to `pool_size` background queries run at the same time, each on its own connection. Any
  extras wait their turn, for up to `acquire_timeout_ms`.
- Queries start in the order you send them, but they can finish in any order. Use the request
  ID to match each result to its query.
- Each background query is saved on its own. Background queries can't be part of a
  transaction you started with `begin_transaction()`.
- Background and normal queries share the same pool, so a lot of background work can make
  normal calls wait for a connection.
- Mistakes such as an unsupported parameter or a missing connection string are reported
  through `async_query_failed` as well. The signal is sent on the next frame, so a handler you
  connect right after making the call will still receive it.
- If you free the adapter while background queries are running, it waits for them to finish
  and then throws their results away.

## API reference

### Methods

- `connect_to_db() -> bool`: opens a connection to check that the database is reachable.
- `disconnect_from_db()`: closes all connections.
- `execute_query(query: String, params: Array = []) -> Array`: runs a query and returns its
  rows, each as a Dictionary. Returns an empty array if it fails.
- `execute_non_query(query: String, params: Array = []) -> int`: runs a statement and returns
  how many rows it changed, or `-1` if it fails.
- `begin_transaction() -> bool`, `commit_transaction() -> bool`, `rollback_transaction() -> bool`
- `execute_query_in_transaction(query, params = []) -> Array`
- `execute_non_query_in_transaction(query, params = []) -> int`
- `is_in_transaction() -> bool`
- `execute_query_async(query, params = []) -> int` and
  `execute_non_query_async(query, params = []) -> int`: start a background query and return
  its request ID.
- `get_last_error() -> String`: the error from the most recent call, or an empty string if it
  succeeded.

### Properties

- `connection_string: String`: where to connect, either as a `postgresql://` URL or in
  PostgreSQL's `key=value` format.
- `pool_size: int`: the most connections the adapter will open at once (default 4).
- `acquire_timeout_ms: int`: how long a call waits for a free connection before giving up
  (default 5000).

### Signals

- `query_failed(query: String, error_message: String)` and
  `non_query_failed(query: String, error_message: String)`: a statement inside a transaction
  failed.
- `query_completed(request_id: int, results: Array)` and
  `non_query_completed(request_id: int, affected_rows: int)`: a background query finished.
- `async_query_failed(request_id: int, query: String, error_message: String)`: a background
  query failed.
- `transaction_started()`, `transaction_committed()`, `transaction_rolled_back()`
- `transaction_failed(error_message: String)`
- `connection_error(error_message: String)`: the adapter couldn't open a connection, or none
  became free in time.

## Parameters and results

Put `$1`, `$2` and so on in your SQL where values go, and pass the values in an array. The
values are sent separately from the SQL, so they're never pasted into it.

You can pass these Godot types:

- `String` and `StringName`
- `int`, `float` and `bool`
- `null`, which becomes SQL `NULL`
- `Vector2`, sent as the text `(x,y)`, which suits PostgreSQL's `point` type
- `Vector3`, sent as the text `(x,y,z)`

Any other type makes the call fail with an error saying which parameter was the problem. There
is no limit on the number of parameters.

Values in the results come back as matching Godot types where there's an obvious match:

- `boolean` becomes `bool`.
- `smallint`, `integer` and `bigint` become `int`.
- `real` and `double precision` become `float`.
- SQL `NULL` becomes `null`.
- Everything else, including `text`, `numeric`, `json`, `uuid` and dates and times, comes back
  as a `String`.

If you want a different type, convert it in your SQL. For example, `price::float8` returns a
`numeric` column as a `float`.

## Connection strings

```
postgresql://[username[:password]@][host][:port][/database][?param=value&...]
```

For example:

- `postgresql://user:pass@localhost:5432/mydb`
- `postgresql://localhost/mydb?connect_timeout=5`

Encrypted (TLS) connections are supported. Add `sslmode=require` to the connection string to
insist on encryption, or `sslmode=verify-full` to also check the server's certificate (point
`sslrootcert` at the certificate authority that signed it). With no `sslmode`, libpq uses
encryption when the server offers it and falls back to an unencrypted connection when it
doesn't, so set `sslmode` whenever the database is on another machine:

- `postgresql://user:pass@db.example.com/mydb?sslmode=verify-full&sslrootcert=/path/to/ca.crt`

## Tests

The `tests/` folder is a small Godot project that tests the adapter against a real database.
The tests create and delete a table called `adapter_test`, so only point them at a database
you don't mind being changed. To guard against accidents, the test runner refuses to run
unless the database's name contains the word `test`. Build the debug version of the
extension first, then run:

```bash
PG_TEST_URL=postgresql://user@127.0.0.1:5432/adapter_test tests/run_tests.sh
```

## Dependencies

- **godot-cpp**, Godot's C++ bindings, included as a git submodule
- **SCons**, the build system
- A **C++20** compiler

`build_scripts/build_third_party.sh` downloads and builds fixed versions of
**libpqxx** and **libpq** (the official PostgreSQL client library) into `third_party/`. They're
then built into the extension itself, so neither you nor your players need PostgreSQL
installed. For encryption, libpq uses the system's OpenSSL 3 libraries (`libssl.so.3` and
`libcrypto.so.3`), so OpenSSL security fixes arrive with ordinary system updates. Apart from
that and the standard C library, the extension has no other runtime dependencies. This copy
of libpq is built without Kerberos or LDAP support.
